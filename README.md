# 图书借阅与管理系统

## 1. 项目简介

本项目为图书借阅与管理系统的需求工程与软件开发管理项目，旨在通过规范化的需求管理、迭代计划、评审、测试、需求跟踪和变更控制，形成完整、可追溯的软件工程过程文档，并为后续系统设计、编码实现、测试和验收提供依据。

项目采用**迭代-增量开发模型**，并在每次迭代中借鉴 **V 模型的验证与确认思想**，使需求、计划、测试和评审相互对应。

项目使用 Git 进行版本控制，使用 GitHub 进行远程仓库管理、团队协作、Pull Request（PR）评审和版本基线管理。

### 1.1 项目目标

- 建立清晰、完整、可追踪的系统需求。
- 制订合理的迭代开发与验证计划。
- 通过交叉评审提高项目文档质量。
- 建立需求与测试之间的双向追踪关系。
- 规范需求变更的申请、审批和影响分析过程。
- 使用 Git/GitHub 记录项目成果、修改历史和评审过程。

### 1.2 系统范围

系统主要围绕图书馆日常业务展开，计划涉及以下功能：

- 用户登录与权限管理。
- 图书信息管理。
- 图书查询。
- 图书借阅与归还。
- 借阅记录管理。
- 图书预约与续借。
- 逾期管理。
- 借阅统计与报表。

具体功能范围、业务规则、优先级及验收标准，以经过评审确认的需求池和需求分析报告为准。

## 2. 项目开发与管理方法

### 2.1 迭代-增量开发模型

项目按照需求优先级、功能依赖关系和开发工作量划分迭代。每轮迭代形成可检查、可验证的阶段性成果，并根据评审和验证结果持续改进。

建议的迭代安排如下：

| 迭代   | 主要功能                                   | 主要验证内容                             |
| ------ | ------------------------------------------ | ---------------------------------------- |
| 迭代 1 | 用户登录、权限管理、图书信息管理、图书查询 | 登录权限、信息维护、查询结果             |
| 迭代 2 | 图书借阅、归还、借阅记录                   | 借阅条件、库存变化、归还处理、数据一致性 |
| 迭代 3 | 图书预约、续借、逾期管理                   | 预约规则、续借条件、逾期处理             |
| 迭代 4 | 统计报表、系统回归测试、整体验收           | 统计正确性、功能回归、系统验收           |

以上迭代划分为初步计划，最终安排以评审通过的《需求规划说明书》为准。

### 2.2 V 模型验证思想

每次迭代均应考虑需求与验证活动之间的对应关系：

- 需求分析阶段：明确功能、业务规则和验收标准。
- 计划与设计阶段：确定实现范围、任务安排和验证策略。
- 实现阶段：根据已确认的需求和设计开展工作。
- 测试阶段：依据测试用例检查实现结果。
- 评审与验收阶段：确认交付成果是否符合要求。

## 4. 文档依赖关系与编写顺序

### 4.1 核心依赖关系

项目按照以下顺序逐步形成文档成果：

1. 需求池提供需求来源、需求编号和初步优先级。
2. 需求分析报告将需求细化为明确的业务流程、功能要求和验收标准。
3. 需求规划说明书依据已明确的需求安排迭代、任务和时间。
4. 测试用例依据需求分析和迭代计划设计。
5. 需求跟踪矩阵关联需求、计划、实现和测试信息。
6. 需求评审记录贯穿各类文档的评审、整改与复核。
7. 变更请求单和影响分析报告依据具体的变更事项开展管理。

### 4.2 文档编写原则

- 需求池与需求分析报告优先完成初稿，并进行第一轮评审。
- 需求分析报告编写期间，可以并行准备规划说明书框架、测试策略和变更管理模板。
- 需求基线建立后，规划说明书、详细测试用例和需求跟踪矩阵可以并行完善。
- 需求跟踪矩阵应随着需求、测试及实现信息逐步更新，不得等到项目结束后凭记忆补填。
- 需求评审记录应在每轮评审后及时更新。
- 变更请求单和影响分析报告可以提前建立模板，但实际记录应以真实变更为依据。模拟案例必须明确标注为模拟案例。
- 上游需求发生变化时，应检查所有依赖文档，并通过变更管理流程更新受影响的内容。

## 6. Git 与 GitHub 版本管理

### 6.1 分支管理策略

项目采用简单的分支协作模式：

- `main`：稳定分支，存放已经通过评审并完成合并的成果。
- `feature/需求获取与分析`：需求相关文档。
- `feature/需求规格说明与评审`：规划和评审文档。
- `feature/需求跟踪矩阵建立`：测试与需求跟踪文档。
- `feature/需求变更控制`：变更管理文档。

所有成员应在各自的功能分支上进行日常修改，不直接向 `main` 推送任务成果。

### 6.2 初始化仓库

仓库管理员在 GitHub 创建仓库，并完成初始目录和说明文件的提交。

```
git clone https://github.com/仓库所有者/Library-Management-System.git
cd Library-Management-System
```

### 6.3 创建个人分支

```
git switch main
git pull --ff-only origin main
git switch -c feature/需求获取与分析
```

其他成员按照各自的分支名称创建分支。

### 6.4 提交修改

完成一个逻辑完整的任务后，检查并提交：

```
git status
git add docs/需求获取与分析/
git commit -m "docs: 完成需求池初稿"
```

`git add` 将指定文件放入暂存区，`git commit` 将本次修改保存到本地 Git 历史中。

### 6.5 推送分支到 GitHub

第一次推送：

```
git push -u origin feature/需求获取与分析
```

后续修改完成并提交后：

```
git push
```

### 6.6 创建 Pull Request

在 GitHub 仓库中进入：

```
Pull requests → New pull request
```

选择：

- **base**：`main`
- **compare**：自己的 `feature` 分支

PR 描述说明修改内容、涉及文件、自检情况及希望评审人重点检查的内容。

PR 创建后，由其他成员交叉评审。发现问题时，负责人在原分支修改并再次提交、推送。

### 6.7 合并 PR

当评审通过、必要的问题整改完成且不存在未解决的合并冲突后，由仓库管理员或团队授权成员执行合并。

采用 GitHub 的 `Create a merge commit` 方式，以保留分支开发和合并历史。

合并完成后：

1. PR 状态变为 `Merged` 并关闭。
2. `main` 包含本次修改。
3. 其他成员同步最新的 `main`。
4. 后续有新的修改时，再发起新的 PR。

### 6.8 同步最新主分支

```
git switch main
git pull --ff-only origin main
```

切回自己的分支并合并最新主分支：

```
git switch feature/需求获取与分析
git merge main
```

如果出现冲突，先根据实际情况解决冲突，再检查修改并完成必要的提交。

建议在开始新任务前，以及准备合并自己的 PR 前，检查并同步最新的 `main`。

## 7. Pull Request 评审规范

每个需要合并到 `main` 的功能分支都应通过 PR 进行评审。

### 7.1 PR 创建前

提交人应确认：

- 当前分支正确。
- 文件名称和存放目录符合规范。
- 需求 ID 没有重复或无故改变。
- 文档与其他相关文档保持一致。
- 本次提交不包含无关修改。
- PR 标题和描述能够说明本次修改目的。

### 7.2 PR 评审期间

评审人应检查：

- 文档内容是否完整、准确。
- 需求与业务规则是否一致。
- 需求、测试和迭代计划之间是否存在矛盾。
- 评审问题是否明确记录。
- 必须整改的问题是否得到解决。

正式评审结论和整改结果应同步更新到《需求评审记录》。

### 7.3 合并要求

- PR 的目标分支应为 `main`。
- 需要整改的问题应在合并前解决。
- 应至少有一名其他成员完成实质性评审并批准。
- 有合并冲突时，应先解决冲突并检查结果。
- 不应将未经评审的文档直接覆盖到 `main`。

建议仓库管理员在 GitHub 的 `Settings` 中为 `main` 配置适用的分支保护规则，要求通过 PR 合并并要求评审批准。

## 8. 需求编号与文档一致性规范

为保证文档之间能够准确关联，项目采用统一编号规则。

| 编号前缀 | 含义               | 示例      |
| -------- | ------------------ | --------- |
| `FR`     | 功能需求           | `FR-001`  |
| `NFR`    | 非功能需求         | `NFR-001` |
| `BR`     | 业务规则           | `BR-001`  |
| `TC`     | 测试用例           | `TC-001`  |
| `RV`     | 评审记录或评审问题 | `RV-001`  |
| `CR`     | 变更请求           | `CR-001`  |
| `IA`     | 影响分析报告       | `IA-001`  |
| `ITER`   | 迭代标识           | `ITER-01` |

具体编号格式可根据课程要求调整，但一经统一，应在所有文档中保持一致。

项目应遵守以下规则：

1. 每项需求具有唯一、稳定的需求 ID。
2. 需求池和需求分析报告中的需求关联应保持一致。
3. 测试用例应关联其验证的需求。
4. 需求跟踪矩阵应关联需求、计划、实现和测试信息。
5. 需求变更时，应保留原有记录，并追踪受影响的文档和测试用例。
6. 尚未确认或尚未实现的内容应如实标记，不得伪造审批、测试或验收状态。

## 9. 需求变更管理

需求基线建立后，新增、删除或修改需求应按照变更管理流程进行处理。

基本流程如下：

1. 提交人填写《变更请求单》。
2. 负责人确认变更原因、目标和关联需求。
3. 编写《影响分析报告》，分析对需求、设计、数据、代码、测试、进度和风险的影响。
4. 由授权人员作出审批决定。
5. 变更获批后，更新相关文档、测试用例和需求跟踪矩阵。
6. 通过 Git 提交和 PR 记录变更内容。
7. 完成必要的验证和复核后，更新变更状态。

## 10. 项目协作流程总结

项目的标准 Git/GitHub 协作流程为：

```
创建 GitHub 仓库
        ↓
初始化目录与 README
        ↓
成员 clone 仓库
        ↓
创建个人 feature 分支
        ↓
编写并检查文档
        ↓
git add → git commit
        ↓
git push
        ↓
创建 Pull Request
        ↓
交叉评审
        ↓
是否需要修改？
   ┌────┴────┐
   │         │
   是        否
   │         │
修改、提交   批准 PR
再次 push      │
   │           │
返回评审       │
   └────┬──────┘
        ↓
合并到 main
        ↓
成员同步最新 main
        ↓
进入下一项任务或迭代
        ↓
里程碑验收后创建版本标签
```

本项目以需求为起点，以评审和验证为质量保障，以需求跟踪矩阵建立跨文档关联，并通过 Git/GitHub 保留修改、评审、合并和版本基线的历史记录，形成可管理、可追踪、可验证的项目工作过程。
